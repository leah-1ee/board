## 문제 내용

`QuicStream.prototype.stopSending()`과 `resetStream()`은 공개 API임에도 `doc/api/quic.md`의 QuicStream 레퍼런스에 누락되어 있었습니다. 두 메서드는 스트림을 한쪽 방향만 닫을 때 사용되며, WebTransport 같은 상위 프로토콜이 의존하는 동작입니다.

원인을 추적한 결과 두 메서드는 `doc/api/quic.md`를 처음 만든 커밋(`062ae6f3cb5`)에서 함께 도입되었으나 문서에만 반영되지 않은 것이었고, 이에 따라 `added:` 필드를 파일의 나머지 항목과 동일한 `v23.8.0`으로 맞췄습니다.

### 기여 내용 — 1차 커밋 (+43 / -1)

- 구현부(`lib/internal/quic/quic.js`)의 JSDoc을 근거로 두 메서드의 시그니처와 동작을 문서화
- 기존에 `writer.fail()`과 `stream.destroy()`만 나열하던 **Aborting a stream** 섹션에 두 메서드를 추가
- 네 방식의 차이를 명시: `writer.fail()`과 `stream.destroy()`는 에러로부터 와이어 코드를 파생시켜 프로토콜의 "internal error" 코드로 폴백하는 반면, `stopSending()`과 `resetStream()`은 인자로 받은 `code`를 그대로 전송

### 기여 내용 — 2차 커밋 (+9 / -4)

1차 커밋을 다시 읽으며 **양방향 스트림의 정상 경로만 서술되어 있다**는 점을 발견해, C++ 구현(`src/quic/streams.cc`의 `Stream::DoStreamReset`, `Stream::SendStopSending`)을 직접 확인하고 누락된 동작 세 가지를 추가로 문서화했습니다.

1. `resetStream()`은 전송 대기 중인 데이터를 폐기함 — 리셋된 스트림은 ACK되지 않으므로 해당 큐가 더 이상 비워질 수 없기 때문
2. 이미 리셋된 스트림에 대한 `resetStream()`은 no-op
3. 단방향 스트림에서 중단하려는 방향이 존재하지 않는 경우(로컬 생성 스트림의 `stopSending()`, 원격 생성 스트림의 `resetStream()`) 프레임을 보내지 않고 조용히 실패함

### 의도적으로 문서화하지 않은 부분

`code`의 유효 범위(62비트)는 문서에 넣지 않고 그 판단 근거를 리뷰에 남겼습니다. 바인딩이 `Uint64Value()`로 값을 읽으며 lossless 플래그를 버리기 때문에, 범위를 넘는 값은 거부되지 않고 조용히 절삭됩니다. 구현이 강제하지 않는 계약을 문서에 명시하면 오히려 잘못된 정보가 되므로 별도 이슈로 다루는 편이 맞다고 판단했습니다.

### 검증 방법

2주차 모임에서 빌드를 직접 경험한 덕분에, 문서 변경도 빌드 파이프라인을 거치는지 먼저 확인했습니다. 그 결과 `doc/api/quic.md`는 Makefile의 `skip_apidoc_files`에 포함되어 **HTML/JSON 문서 빌드 대상이 아니며 `make doc-only`로는 검증되지 않는다**는 사실을 확인하고, 대체 검증 경로를 사용했습니다. 이 내용은 PR 본문에도 명시했습니다.

- `node tools/lint-md/lint-md.mjs doc/api/quic.md` — 통과
- `python3 tools/test.py doctool` — 3/3 통과
- 앵커가 파일의 기존 컨벤션(`stream.setPriority([options])` → `#streamsetpriorityoptions`)을 따르는지 수동 확인

### 트러블슈팅 — 커밋 큐 실패 대응

리뷰 승인 후 `commit-queue` 라벨이 부여되었으나 큐가 실패했습니다. 실행 로그와 `tools/actions/commit-queue.sh`를 확인한 결과, **커밋이 2개 이상인 PR에 랜딩 전략 라벨이 없으면 기본값인 `--oneCommitMax`에 걸려 중단**되는 것이 원인이었습니다. 커밋 2개가 자동으로 스쿼시되지는 않습니다.

두 번째 커밋이 첫 번째 커밋이 추가한 섹션을 확장하는 내용이라 히스토리를 분리할 이유가 없다고 판단해, `commit-queue-squash` 라벨과 함께 `commit-queue` 라벨 재부착을 요청하는 코멘트를 남겼습니다(실패한 실행에서 봇이 후자를 제거했기 때문). 이후 정상적으로 머지되었습니다.

> 참고: 이 이슈는 선행 PR #63681이 있었으나 랜딩되지 않고 닫힌 상태였습니다. 착수 전 이를 확인하고 PR 본문에 supersede 사실을 명시했습니다.

## 기여 회고

### 1. 중복 작업 확인은 이슈 코멘트만으로는 부족하다

이슈 #64704에서 이미 수정 PR이 존재하는 이슈에 분석 시간을 투입했습니다. 이슈에 달린 코멘트만 읽어서는 알 수 없고, **이슈의 cross-reference 타임라인에서 연결된 PR을 확인**해야 한다는 점을 배웠습니다. 이후 #63680에 착수할 때는 이 절차를 먼저 수행해 선행 PR #63681이 랜딩되지 않고 닫힌 것을 확인한 뒤, 그 사실을 PR 본문에 명시했습니다.

### 2. 문서 기여는 구현이 실제로 보장하는 것만 써야 한다

문서 PR이라도 JSDoc을 옮겨 적는 것으로는 부족했습니다. 1차 커밋을 올린 뒤 스스로 다시 읽으며 양방향 스트림의 정상 경로만 서술되어 있음을 발견해 C++ 구현까지 내려가 확인했고, 누락된 엣지 케이스 세 가지를 2차 커밋으로 보강했습니다.

반대로 `code`의 유효 범위는 구현이 강제하지 않기 때문에 **일부러 쓰지 않았습니다**. 문서에 적는 순간 그것은 프로젝트의 약속이 되므로, 구현이 지키지 않는 내용을 쓰면 오히려 잘못된 정보를 남기게 된다는 기준을 세우게 된 계기였습니다.

### 3. 배운 규칙이 실제 기여에서 어떻게 작동하는지

3주차에 학습한 Organization 역할과 규칙은 이후 기여 전 과정에서 그대로 쓰였습니다.

- 커밋 메시지 컨벤션, `Fixes:` / `Refs:` 메타데이터, DCO sign-off, rebase 전략
- 커밋 큐 라벨 체계 — `commit-queue`, `commit-queue-squash`, `commit-queue-rebase`의 역할과 `-oneCommitMax` 기본 동작

특히 CI가 실패했을 때 로그를 읽고 스크립트까지 확인해 원인을 특정한 뒤, 메인테이너가 바로 조치할 수 있도록 **필요한 라벨을 구체적으로 지목해 코멘트를 남긴 경험**이 인상적이었습니다. 리뷰어의 시간이 프로젝트에서 가장 희소한 자원이라는 것을 체감했습니다.
