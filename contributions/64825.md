### WPT 테스트로 개선 점 찾기

같이 오픈소스 컨트리뷰션 진행하는 동료분의 머지된 PR을 확인해보았습니다.

개선 점을 요약하자면, slice의 소수점을 개선하여 웹 표준에 맞췄다는 내용입니다.

해당 부분을 어떻게 찾아서 개선했을까 궁금했는데, 동료분께서 친절하게 설명해주셨습니다.

그래서 저도 WPT를 통해서 Fail 부분을 찾아 기여해보기로 했습니다.

#### WPT란?

web-platform-tests(WPT)는 브라우저나 런타임이 웹 표준을 올바르게 구현했는지 검증하는 공통 테스트 모음입니다.

예를 들어서 다음 구현들이 표준대로 동작하는지를 테스트합니다.

- fetch
- URL
- Blob, File
- Web Streams
- DOM 등

이를테면 다음 테스트와 같습니다.

```js
const blob = new Blob(['hello']);

console.log(blob.size); // 반드시 5여야 함
```

여기에서 웹 브라우저나 다른 것들에 따라서, size가 5가 아닌 4나 6이 나올 수도 있습니다. 근데 표준은 5인거죠. 이를 표준에 맞추는 테스트모음이 WPT라고 할 수 있습니다.

다음 링크를 통해서, Node.js 뿐만 아니라 다양한 프레임워크가 WPT를 통과하는지를 확인할 수 있습니다.

### 해당 테스트 코드 이해하기

실패한 테스트 코드는 다음과 같습니다.

```js
promise_test(async t => {
  let ctrl;  // stream 관리 control
  let abortPromise;  // 첫 번째 abort 요청이 종료됨을 나타내는 promise
  let abortPromiseFromSignal;  // 두 번째 abort 요청이 좀료됨을 나타내는 promise

  const e1 = SyntaxError();
  const e2 = TypeError();
  const ws = new WritableStream({
    start(c) { ctrl = c; }, // start는 스트림 준비 시, 실행되는 초기화 함수
  }); // 여기에서 c는 스트림 관리 리모컨이다.
  // ctrl.signal 을 입력하면, 상태를 알아낼 수 있다.

  const writer = ws.getWriter();  // 쓰기 작업자

// 중단 신호 감시
  ctrl.signal.addEventListener('abort', () => {
    abortPromiseFromSignal = writer.abort(e2);
  });
  abortPromise = writer.abort(e1); // 즉시 abort가 안될 수 있으므로 Promise로 반환
  assert_true(ctrl.signal.aborted); // abort 성공 했는지 확인

  await Promise.all([
    abortPromise,
    abortPromiseFromSignal,
    promise_rejects_exactly(t, e2, writer.closed, 'closed')
  ]);
}, 'recursive abort() call from abort() aborting signal (not started)');
```

#### writer

writer는 WritableStream 작업자.

아래처럼 사용 가능함.

- writer.write(data) : 데이터 넣기
- writer.close() : 작업 종료
- writer.abort(reason) : 문제가 발생해서 강제 중단

#### signal.addEventListener()

“이벤트를 감지해서, 해당 이벤트 발생 시에 이 함수를 실행해주세요!” 라는 의미이다.

```js
ctrl.signal.addEventListener('abort', () => {
  abortPromiseFromSignal = writer.abort(e2);
});
```

여기에서는 ‘abort’ 이벤트 발생 시에, abortPromiseFromSignal = writer.abort(e2); 을 실행해달라는 요청이다.

#### abort 호출 테스트

그 아래 코드 보면 e1을 발생시키는 코드가 있다.

```js
abortPromise = writer.abort(e1);
```

의도적으로 e1이라는 이유로 abort 를 발생시켰다. 이전에 abort 시에 호출하도록 만든 이벤트가 있는데, 이를 바탕으로 테스트 흐름을 설명하면 다음과 같다.

1. writer.abort(e1) 호출
2. ctrl.signal을 aborted 상태로 변경
3. abort 이벤트 발생
4. 등록해 둔 이벤트 함수 실행
5. 이벤트 함수 안에서 writer.abort(e2) 호출
6. 이후 다시 abort(e1)으로 돌아가서 나머지 작업 처리 ## 여기 부분이 문제
7. 스트림이 오류 상태로 변경

#### 마지막 Promise.all()

```js
await Promise.all([
  abortPromise,
  abortPromiseFromSignal,
  promise_rejects_exactly(t, e2, writer.closed, 'closed')
]);
```

하나씩 확인해보자.

- abortPromise: 첫 번째 abort 요청이 정상적으로 되는지 확인하는 테스트
- abortPromiseFromSignal : 두번째 (e2)도 abort가 됐는지 확인
- promise_rejects_exactly(t, e2, writer.closed, 'closed')  이게 중요하다.

#### promise_rejects_exactly(t, e2, writer.closed, 'closed')

Stream이 최종적으로 어떻게 종료되었는지를 확인하는 테스트.

테스트 의미를 해석하면,

writer.closed가 반드시 실패해야 하고, 그 실패 이유는 정확히 e2 객체여야 한다

왜 closed가 실패해야하냐면, 정상 종료(close)가 아니라 abort로 종료되었기 때문이다.

e2 : 이게 실패의 주요 원인이다. 실패 사유가 e2이어야하는데, e1이 되어서 실패하는 것이다.

#### 최종 해석

현재 흐름을 다음과 같다.

abort(e2)를 통해 스트림 상태를 결정했다면, 이를 호출한 abort(e1)이 해당 상태를 다시 변경하거나 덮어쓰면 안된다.

```js
class WritableStreamDefaultWriter {
  [kType] = 'WritableStreamDefaultWriter';

  /**
   * @param {WritableStream} stream
   */
  constructor(stream) {
    if (!isWritableStream(stream))
      throw new ERR_INVALID_ARG_TYPE('stream', 'WritableStream', stream);
    this[kState] = {
      stream: undefined,
      // Lazily materialized by writerClosedPromise()/writerReadyPromise().
      close: undefined,
      ready: undefined,
    };
    setupWritableStreamDefaultWriter(this, stream);
  }
```

kType에는 3개 존재

- stream
- close
- ready

## 해결 과정과 검증

### 변경한 코드

```js
function writableStreamAbort(stream, reason) {
  const { controller } = stream[kState];

  let state = stream[kState].state;
  if (state === 'closed' || state === 'errored')
    return PromiseResolve();

  controller[kState].abortController.abort(reason);

  state = stream[kState].state;
  if (state === 'closed' || state === 'errored')
    return PromiseResolve();

  if (stream[kState].pendingAbortRequest.abort.promise !== undefined)
    return stream[kState].pendingAbortRequest.abort.promise;

  assert(state === 'writable' || state === 'erroring');

  let wasAlreadyErroring = false;
  if (state === 'erroring') {
    wasAlreadyErroring = true;
    reason = undefined;
  }

  const abort = PromiseWithResolvers();

  stream[kState].pendingAbortRequest = {
    abort,
    reason,
    wasAlreadyErroring,
  };

  if (!wasAlreadyErroring)
    writableStreamStartErroring(stream, reason);

  return abort.promise;
}
```

### 기존 코드

```js
function writableStreamRejectCloseAndClosedPromiseIfNeeded(stream) {
  assert(stream[kState].state === 'errored');
  if (stream[kState].closeRequest.promise !== undefined) {
    assert(stream[kState].inFlightCloseRequest.promise === undefined);
    stream[kState].closeRequest.reject(stream[kState].storedError);
    stream[kState].closeRequest = kNilRequest;
    stream[kState].closeQueuedOrInFlight = false;
  }

  const closedPromiseCache = stream[kState].closedPromise;
  if (closedPromiseCache !== undefined) {
    setPromiseHandled(closedPromiseCache.promise);
    closedPromiseCache.reject(stream[kState].storedError);
  }

  const {
    writer,
  } = stream[kState];
  if (writer !== undefined) {
    const closeCache = writer[kState].close;
    if (closeCache !== undefined) {
      setPromiseHandled(closeCache.promise);
      closeCache.reject(stream[kState].storedError);
    }
  }
}
```

### 다음 코드로 수정

close state가 3개 있다.

- close request
- stream의 close
- writer의 close

각각 모두 promise 객체이고, 별도로 관리가 필요하다.

이전에 실패한 테스트 에러는 writer의 close에서 발생한 것인데, 이미 상태가 reject 되었는데 다시 if 로직에 들어와 reject 되었기에 문제가 발생한 것임.

그래서 if 조건문에 해당 Promise가 pending 인지를 확인하는 로직을 추가하여 검증함.

### 이미 알고리즘 표준이 다 만들어져 있구나?

Stream 로직을 읽고, 이에 대한 표준 문서를 읽으면서 놀랐다.

writable stream(쓰기 전용 스트림)에 대한 기능 및 알고리즘이 이미 다 표준으로 나와있기 때문이다. 즉, 개발자가 머리 싸매면서 writable stream을 만드는게 아니라, 표준에 맞춰서 그냥 구현만 하면 된다.

#### 복잡한 상태값과 왜 있는지 모르겠는 값들

상태가 왜 이렇게 많은지 모르겠다.

실제로 내가 어려웠던 부분의 코드이다.

```js
function writableStreamRejectCloseAndClosedPromiseIfNeeded(stream) {
  assert(stream[kState].state === 'errored');
  if (stream[kState].closeRequest.promise !== undefined) {
    assert(stream[kState].inFlightCloseRequest.promise === undefined);
    stream[kState].closeRequest.reject(stream[kState].storedError);
    stream[kState].closeRequest = kNilRequest;
    stream[kState].closeQueuedOrInFlight = false;
  }

  const closedPromiseCache = stream[kState].closedPromise;
  if (closedPromiseCache !== undefined) {
    setPromiseHandled(closedPromiseCache.promise);
    closedPromiseCache.reject(stream[kState].storedError);
  }

  const {
    writer,
  } = stream[kState];
  if (writer !== undefined) {
    const closeCache = writer[kState].close;
    if (closeCache !== undefined) {
      setPromiseHandled(closeCache.promise);
      closeCache.reject(stream[kState].storedError);
    }
  }
}
```

보면, close와 관련된 상태가 3개가 있다.

- stream[kState].closeRequest
- stream[kState].closedPromise
- writer[kState].close

이 값을 보자마자 든 질문 1개는

“그냥 stream을 닫는 용도의 close 하나만 상태로 두면 되는거 아니야?”

또다른 의문점으로 cache가 있다.

- closedPromiseCache = stream[kState].closedPromise
- closeCache = writer[kState].close

이걸 보고 다음 궁금증이 생겼다.

“아니 cache 왜 써야해? 안쓰고 하면 되는거 아니야? ”

사실 이런 의도를 내가 코드를 하나하나 까보면서, 파악하기는 정말 어려웠다. 그래서 AI의 도움을 받았고 이를 이해할 수 있었다.

#### 언제 호출되는지 모를 함수들

위 코드를 그대로 가져와보자.

```js
function writableStreamRejectCloseAndClosedPromiseIfNeeded(stream) {...}
```

함수 이름이 참 보고도 뭔 소린지 모르겠다. 디버깅하기 위해서 breakpoint 잡아봐도 안잡혀서, 언제 호출되는 지도 잘 모르겠다.

Node.js Stream 공식 문서에는 안나와있고, Streams 공식 문서에는 나와있다.

그런데, 이게 어떤 순간에 호출되고 어떤 역할로 만든건지는 안나와있어서, 직접 역추적하면서 추론해야한다. 이게 정말 어렵다고 생각이 들어서 AI를 적극적으로 활용해서 이해하려고 했던 것 같다.

나는 영어 작문 실력이 썩 좋지 못하다. 의미는 전달할 수 있는데, 해당 단어가 그 상황에 맞는지 파악을 잘 못한다. 그래서 AI의 도움을 받아서 커밋 메시지와 PR 메시지를 작성했는데, 해당 능력을 기를 필요성을 많이 느낀다.

(한국어의 경우, AI로 글을 작성하면 대충 티가 나서, 영어로 그런 티가 날까봐 걱정됐다. 그래서 AI 3개로 검증을 했다…)
